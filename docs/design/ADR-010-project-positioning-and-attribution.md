# ADR-010: Project Positioning, Disclaimers & Attribution

## Status
**Accepted**

## Context
`zeroasterisk/aaif-wiki` reads the repositories of the **Agentic AI Foundation** — a Linux Foundation
project that stewards MCP, goose, AGENTS.MD, and agentgateway — and publishes a derived wiki *about*
AAIF. It is built by one person, on personal time, and is **not** an AAIF project.

That gap between what it is and what it looks like is the whole problem this ADR exists to close:

1. **It will be mistaken for official.** A tidy, machine-maintained wiki named `aaif-wiki`, full of
   working-group pages and confident summaries, published on GitHub Pages, reads as authoritative.
   Someone will cite it as AAIF's position. AAIF has 7 working groups (Identity and Trust;
   Governance, Risk and Regulatory; Workflows and Process Integration; Accuracy and Reliability;
   Security and Privacy; Agentic Commerce; Observability and Traceability) plus 1 cross-group
   workstream (Taxonomy and Landscape); an unofficial page summarizing any of them can drift from
   what the group actually decided, and the reader has no way to know.
2. **The content is derived from other people's licensed work.** AAIF repositories carry licenses —
   Linux Foundation projects are typically Apache-2.0 for code and CC-BY-4.0 for documents and
   specifications, but **the applicable license is whatever each repository's own LICENSE file
   says**, and that must be read per repository rather than assumed. Derived pages inherit
   obligations, principally attribution.
3. **Donation is the intended endpoint.** The project is explicitly built to be handed to AAIF. That
   only works if provenance, licensing, and disclaimers are correct from the first commit —
   retrofitting attribution onto a corpus that has been running for a year is miserable and
   sometimes impossible.

## Decision
Position the project as **unofficial, attributed, and donation-ready** — enforced by validators and
templates, not by good intentions.

### 1. Disclaimer in three places, non-negotiable
The same disclaimer text, from a single source (`aaif_wiki/templates/disclaimer.md`), appears in:

| Location | Placement |
| :--- | :--- |
| `README.md` | Directly under the H1, above everything else, before any description of features. |
| Wiki bundle root `wiki/index.md` | In the body, immediately after the H1 — so it is visible on GitHub, on Pages, and in Obsidian, and it travels with the bundle if the bundle is copied elsewhere. |
| Any published digest (Gist, exported briefing) | In the **header**, before the content — not a footer. |

Text:

> **Unofficial.** This is a personal project by [@zeroasterisk](https://github.com/zeroasterisk).
> It is **not** affiliated with, endorsed by, or reviewed by the Agentic AI Foundation or the Linux
> Foundation. Pages here are generated by an automated pipeline from public AAIF repositories and
> may be incomplete, out of date, or wrong. **For authoritative information, follow the canonical
> upstream source linked on every page.** Pages marked `status: draft` have not been reviewed by a
> human.

Enforced by a deterministic validator (ADR-008 Layer 1): the disclaimer's presence in `README.md`
and `wiki/index.md` is checked in CI, and every exporter injects it into published artifacts as part
of `sanitize()` (ADR-007 §4). It cannot be forgotten and it cannot be edited out of one copy while
staying in another, because there is only one copy.

### 2. Every concept links to its canonical upstream source
Not a courtesy — the mechanism by which a reader gets from a derived summary to the real thing.

- Every concept carries OKF `resource` pointing at the canonical upstream URL: the repository, file,
  PR, issue, or discussion it summarizes.
- Every concept carries `sources[]` with per-source entries resolving to the actual upstream
  artifact (ADR-003 pointer events resolve to `github.com/<repo>/blob/<commit_sha>/<path>` —
  commit-pinned, so the link shows what was actually read, not what the file says today).
- Per-claim attribution uses markdown footnotes keyed to the source id, e.g. `[^evt-spaa-pr11]`, per
  OKF v0.2. The v0.1 body `# Citations` list is superseded by frontmatter `sources` and must not be
  emitted.
- Every page renders an **"Upstream source"** line near the top, above the fold, not buried in a
  references section at the bottom.

Validators V3 (provenance integrity) and V5 (OKF conformance) in ADR-008 make a concept without
resolvable provenance a build failure.

### 3. Licensing and attribution of ingested content
1. **Detect, do not assume.** Ingestion records each source repository's license from its `LICENSE`
   file and GitHub's license metadata into the repo-discovery event (ADR-003 §6). LF projects are
   *typically* Apache-2.0 or CC-BY-4.0, but the per-repository LICENSE file is the only authority
   and is what gets recorded.
2. **Carry it into derived pages.** Every concept's frontmatter records the license(s) of its
   sources under a namespaced producer extension (OKF v0.2 has no license field), and the rendered
   page states, near the upstream link: *"Derived from `aaif/<repo>` (`<license>`)."*
3. **Attribution is satisfied concretely.** CC-BY-4.0 requires attribution, a license link, and an
   indication of changes. Each page therefore names the upstream repository, links the license,
   links the commit-pinned source, and states that the content is a machine-generated summary — an
   explicit indication of modification.
4. **`wiki/ATTRIBUTION.md`** aggregates, per source repository: upstream URL, detected license,
   license URL, and the concepts derived from it. One page a lawyer or a maintainer can read.
5. **Quote sparingly, summarize by default.** The pipeline produces summaries, not reproductions.
   Where verbatim text is used it is block-quoted and attributed inline.
6. **The project's own license** applies to the pipeline code and to the generated prose; it does
   not and cannot relicense upstream content, and `ATTRIBUTION.md` says so.
7. **Honest limit:** license detection is mechanical and can be wrong — mixed-license repositories,
   a `LICENSE` covering code while `docs/` carries something else, vendored third-party material.
   Detected licenses are recorded as *detected*, and where detection is ambiguous the page says
   "license: see upstream" rather than guessing.

### 4. Donation path
Stated in the README so the intent is public rather than private:

- AAIF accepts new projects through its **`project-proposals`** repository. Donation would proceed
  by opening a proposal there and following whatever process AAIF's Technical Advisory Council
  applies. *(The specific requirements of that process are AAIF's to define and are not restated
  here; nothing in this ADR should be read as describing AAIF's acceptance criteria.)*
- **What is donatable, in decreasing order of independence:**

  | Artifact | Donatable on its own? |
  | :--- | :--- |
  | The generic OKF MCP server (ADR-007 §0) | **Yes, today.** Bundle-agnostic; reads any OKF v0.2 bundle. Useful to the OKF/AAIF ecosystem with zero reference to this project. |
  | The OKF v0.2 bundle in `wiki/` | Yes. Plain Markdown in git, no runtime, readable with `cat`. |
  | The event store and review records | Yes, and they are what make the bundle auditable and re-derivable rather than a pile of generated text. |
  | The pipeline | Yes, with a caveat stated plainly: it hard-depends on `google-adk` and `google-genai` (ADR-005). Portability is a property of the **output**, not the pipeline. |

- **Preconditions we hold ourselves to before proposing:** the bundle passes all ADR-008 Layer 1
  validators; `ATTRIBUTION.md` is complete; no corporate paths or internal references anywhere in
  history (ADR-007 §2); and a meaningful fraction of the corpus is `verified` by a human rather than
  sitting at `draft`.
- **If AAIF declines, or never responds,** the project continues as an unofficial personal wiki with
  the disclaimers above. Donation is the intent, not a dependency.

### 5. Naming
The repository is `zeroasterisk/aaif-wiki` — personal namespace, which is itself a signal. It is
never described as "the AAIF wiki." Self-description is consistently *"an unofficial, automatically
generated wiki about AAIF."* If AAIF ever objects to the name, we rename; the name is not worth an
argument with the foundation we are trying to give the thing to.

## Consequences

### Positive
* **Misattribution risk drops sharply.** A disclaimer at the top of the README, the bundle index, and
  every digest is hard to miss and hard to strip, since all three come from one file that CI checks.
* **Attribution obligations are met by construction**, not by a cleanup pass — the license flows from
  repo discovery through the event into the page.
* **Commit-pinned source links are better than courtesy citations.** A reader sees exactly what was
  read, even if upstream has since changed.
* **The generic MCP server is immediately useful to others**, which is a far stronger donation
  argument than "here is a wiki about you."
* **Stating the donation path publicly** invites correction from AAIF early, when it is cheap.

### Negative / Trade-offs
* **Disclaimer fatigue.** The same block on the README, the index, and every digest is visual noise,
  and regular readers will stop seeing it. We accept the noise; the alternative failure is worse.
* **License detection is heuristic.** Mixed-license repositories will occasionally be labelled
  wrong. Mitigated by recording licenses as *detected* and by `ATTRIBUTION.md` being reviewable, not
  by pretending the detection is authoritative.
* **The disclaimer undercuts the product.** Telling every reader the content may be wrong and to go
  read the source is honest and does reduce the wiki's perceived value. That is the correct trade
  for an unofficial derivative.
* **Donation may not happen.** Effort spent on attribution rigor, generic tooling, and provenance is
  spent regardless of whether AAIF ever accepts. It is defensible on its own merits, but it is real
  cost incurred for an uncertain outcome.
* **The `verified`-coverage precondition is a real gate.** With one reviewer (ADR-009), reaching
  meaningful human-verified coverage before proposing donation could take a long time.
